# Полные зашифрованные резервные копии InsFlow

## Статус и расписание

Реализован отдельный контур резервирования БД, документов и настроек в существующий канал VK.
Эта инструкция описывает код и порядок эксплуатации. **Первый production-прогон, скачивание, расшифровка
ключом владельца и совместное восстановление новой копии пока не подтверждены этой записью.**
Фактический отчёт добавляется после проверки; прежний результат восстановления только БД сохранён
в [журнале проверок](backup_restore_verification.md).

| Время, МСК | Задача | Содержимое |
|---|---|---|
| 03:00 ежедневно | Прежний `send_backup_to_vk` | PostgreSQL dump; при сбое — явно обозначенная аварийная JSON-выгрузка |
| 03:15 ежедневно | Новый `run_recovery_backup.py` | Зашифрованный комплект: PostgreSQL dump + `media` + настройки + исходный код |

Это независимые запуски и разные снимки БД. Новая задача не заменяет и не меняет задачу 03:00.
Установщик использует `CRON_TZ=Europe/Moscow` и маркер `# insflow-recovery-vk`.
После подготовки конфигурации он устанавливается от пользователя деплоя; workflow повторяет установку
после релиза. `--allow-unconfigured` пропускает установку при отсутствующей конфигурации, но не скрывает
ошибку существующей некорректной конфигурации. Наличие кода в Git само по себе не означает, что cron установлен.

## Как создаётся копия

1. `backup/recovery_snapshot.py` открывает новую PostgreSQL-транзакцию `REPEATABLE READ, READ ONLY`,
   экспортирует её snapshot и передаёт идентификатор в настоящий `pg_dump --snapshot`.
   Количества строк таблиц и ссылки всех зарегистрированных `FileField` читаются в той же транзакции.
   Пароль передаётся `pg_dump` через окружение, без аргументов командной строки и вывода в лог.
2. Копируются **все обычные файлы** `media`, включая файлы без текущих ссылок из БД. Каждый файл, указанный
   в файловом поле БД, должен существовать. Симлинки, специальные файлы, небезопасные ссылки и замеченные
   изменения дерева/содержимого отменяют запуск. Для файлов сохраняются размеры и SHA-256.
3. `pg_restore --file=/dev/null` полностью читает custom-архив, не подключаясь к БД. Только после успешных
   проверок приватный временный каталог атомарно публикуется с `manifest.json` и маркером `READY`.
   Состояния последовательностей берутся из дампа при восстановлении; отдельно из меняющейся рабочей БД
   они для manifest не запрашиваются.
4. `scripts/create_recovery_bundle.py` проверяет снимок, соответствие кода работающему релизу и стабильность
   конфигурации, добавляет настройки и исходники, затем передаёт tar-поток в `age` для шифрования X25519.
   Готовый ZIP публикуется атомарно. В ZIP ровно два файла: `payload.tar.age` и общая инструкция `README.txt`.
5. `scripts/run_recovery_backup.py` передаёт **точный архив этого запуска** через `send_recovery_to_vk`,
   сохраняет приватную квитанцию и скачивает документ обратно через `download_recovery_from_vk`.
   Сверяются размер и SHA-256. Только после совпадения отмечается `verified_download=true`, обновляется
   `last_success.json` и разрешается ротация подтверждённых локальных копий.

Параллельный запуск этой же задачи блокируется `flock`. Повторная отправка того же файла с подходящей
квитанцией возвращает `already_sent`; проверка скачивания всё равно выполняется.
Успешное скачивание зашифрованных байтов не является проверкой расшифровки или восстановления приложения.

## Что находится внутри зашифрованного tar

| Путь | Содержимое |
|---|---|
| `database.dump` | Полный custom dump базы приложения, включая пользователей, группы и права Django |
| `media/` | Скопированные документы, ответы, своды, шаблоны и прочие обычные файлы `MEDIA_ROOT` |
| `snapshot_manifest.json` | Snapshot БД, количества строк таблиц, ссылки на файлы, размеры и контрольные суммы |
| `config/.env` | Конфигурация приложения, в том числе секреты; доступна только после расшифровки |
| `config/docker-compose.yml` | Конфигурация контейнеров проекта |
| `config/nginx.conf`, при наличии `nginx-acme.conf` | Используемые файлы Nginx из каталога проекта |
| `config/tls.tar` | `/etc/letsencrypt` из Nginx-контейнера, включая сертификаты и их приватные ключи |
| `config/insflow.crontab` | Только строки crontab с маркерами `# insflow-*` |
| `config/runtime.json` | Версии Python/Django/пакетов, build SHA, образ, digests и сведения о mounts |
| `source.tar` | Отслеживаемые Git исходники точного коммита работающего приложения |
| `manifest.json` | SHA-256, размеры и исходные права/владельцы файлов комплекта, метаданные сборки |

Это комплект приложения, а не образ диска сервера. В него не входят история Git, произвольные неотслеживаемые
файлы, ОС, настройки SSH, учётные записи хоста, кабинет провайдера/DNS и данные других сервисов.
Подготовка нового хоста, доступы к реестру образов, восстановление маршрутизации и переключение трафика
остаются отдельными операциями. UID/GID из manifest — сведения для сопоставления с новой средой,
а не указание слепо применять старых владельцев на новом хосте.

## Ключ, размещение и срок хранения

- **Приватный ключ `age` хранится только на Mac владельца**, отдельно от production, VK и репозитория.
  На сервер передаётся только публичный получатель `age1…`. Приватного ключа нет в архиве, `.env`, CI или
  конфигурации cron. Потеря единственного пригодного приватного ключа делает расшифровку невозможной.
- Конфигурация пользователя деплоя: `~/.config/insflow-recovery/config.json`, права `0600`, владелец —
  запускающий пользователь. Поля: абсолютные пути `age_binary`, `recipient_file`, `state_dir`, `keep_local: 14`.
  Пример без реальных значений:

  ```json
  {
    "age_binary": "/absolute/path/to/age",
    "recipient_file": "/absolute/path/to/recipient.txt",
    "state_dir": "/absolute/path/to/private/recovery-state",
    "keep_local": 14
  }
  ```

- По умолчанию state: `~/.local/state/insflow-recovery`, приватный каталог `0700` вне volumes приложения.
  `exports/` содержит зашифрованные ZIP; `receipts/` — квитанции `0600`; `runs/` и `last_success.json` —
  результаты запусков без токенов и ссылок доступа. Квитанции содержат VK `access_key`: их нельзя выводить
  в общие логи, чат или Git. Реальные имена клиентских файлов есть только внутри приватного manifest.
- Локально сохраняются **последние 14 копий с подтверждённым обратным скачиванием** (по мере их накопления). Ротация выполняется после
  нового успешного запуска. При ошибке прежние подтверждённые копии и `last_success.json` сохраняются;
  старые неуспешные зашифрованные архивы могут удаляться отдельно, чтобы ограничить накопление.
- Документы и сообщения **в VK автоматически не удаляются**. Это не гарантия бессрочного хранения со
  стороны VK; доступность канала и достаточное место необходимо контролировать.
- Ограничение отправки — **190 MiB = 199 229 440 байт** для целого ZIP. Превышение завершает запуск ошибкой,
  без отправки старого архива или замены комплекта неполным файлом. При приближении к лимиту требуется
  отдельное решение о хранилище/формате, а не молчаливое исключение документов.

Незашифрованные промежуточные файлы находятся в приватных временных каталогах и очищаются при штатном
завершении обработки ошибок. После принудительного завершения процесса или сбоя хоста следует отдельно
проверить оставшиеся временные каталоги; их наличие не означает готовую копию.

## Контроль запуска

Для ручного штатного запуска от пользователя деплоя, **с созданием копии и отправкой в VK**:

```bash
python3 scripts/run_recovery_backup.py
```

Для установки отдельного ежедневного расписания после подготовки конфигурации:

```bash
bash scripts/recovery-cron-setup.sh
```

Лог обёртки: `logs/cron_recovery_backup.log`. Успех — JSON `status=success`, `verified_download=true`,
совпавшие SHA-256/размер и актуальный `last_success.json`. Сообщение «отправлено» без обратной проверки
для этого контура недостаточно. При ошибке отправляется общее уведомление в существующий VK-канал;
доставка уведомления тоже может не состояться, её результат сохраняется отдельно.
Ошибка очистки или ротации отражается в результате и требует внимания, даже если доставка уже подтверждена.

Проверять нужно также время последнего успеха: аварийное завершение процесса, сбой cron или недоступность
самого хоста могут помешать отправке уведомления. Внешний мониторинг отсутствия ночной копии этим кодом
не создаётся.

## Восстановление и пробная проверка

1. Выбрать конкретную копию в VK. На работающем сервере её можно скачать командой
   `download_recovery_from_vk --receipt-file <приватная-квитанция> --output-file <новый-файл>` внутри web-контейнера:
   команда проверяет метаданные документа, размер и SHA-256. При потере сервера владелец скачивает ZIP
   из вложения в том же VK-канале вручную. Сохранить название, дату, размер и SHA-256; сравнить контрольную сумму
   скачанного ZIP с SHA-256 в успешном сообщении VK, а при наличии независимой квитанции — также с ней.
   Это позволяет сверить выбранную копию и при недоступном исходном сервере.
2. На Mac владельца проверить ZIP и расшифровать его в новый приватный каталог. Приватный ключ на сервер
   для этого не переносится. Ниже — шаблон; указать пути выбранного ZIP и уже сохранённого ключа:

   ```bash
   umask 077
   RECOVERY_ZIP='/absolute/path/to/insflow_recovery_<id>.zip'
   RECOVERY_WORK="$(mktemp -d "${TMPDIR:-/tmp}/insflow-recovery.XXXXXX")"
   unzip -t "$RECOVERY_ZIP"
   shasum -a 256 "$RECOVERY_ZIP"
   unzip -p "$RECOVERY_ZIP" payload.tar.age > "$RECOVERY_WORK/payload.tar.age"
   age --decrypt --identity '/absolute/path/to/owner-key.txt' \
     --output "$RECOVERY_WORK/payload.tar.part" "$RECOVERY_WORK/payload.tar.age" && \
     mv "$RECOVERY_WORK/payload.tar.part" "$RECOVERY_WORK/payload.tar"
   ```

   Продолжать только после успешного завершения `age`; частичный tar не использовать. Восстановление не
   предполагает вывода `.env`, ключей, signed URL или клиентских документов в терминал/общие логи.
3. Проверить список членов tar до распаковки: только ожидаемые относительные пути комплекта, без `..`,
   абсолютных путей, симлинков и специальных файлов. Распаковать в отдельный приватный каталог, не в корень
   хоста. Проверить SHA-256 и размеры **всех** файлов по `manifest.json`, затем данные по `snapshot_manifest.json`,
   включая наличие каждого файлового пути из БД. Служебные `source.tar` и `config/tls.tar` на этом шаге
   остаются обычными файлами; их не распаковывают поверх рабочего проекта или `/etc`.
4. Поднять отдельный PostgreSQL 15 с пустой БД, собственным volume и Unix socket, без внешней сети,
   опубликованных портов и production volumes. Восстановить весь `database.dump`:

   ```bash
   pg_restore --exit-on-error --single-transaction --no-owner --no-acl \
     --host /path/to/isolated/socket --username restore_user \
     --dbname isolated_restore /path/to/decrypted/database.dump
   ```

   Имя БД, socket и пользователь здесь относятся только к стенду. Сверить таблицы и количества строк с
   snapshot manifest; состояния последовательностей — с `setval` самого дампа **до** тестовых записей.
   Проверить ограничения, индексы и внешние ключи. Пароли не передавать через argv.
5. Запустить исходники/образ соответствующего build SHA с восстановленной БД и **документами из этого же
   комплекта**. Для стенда использовать собственные настройки, отключить внешние отправки и фоновые задачи,
   обойти entrypoint с автоматическими миграциями. Production `.env` не загружать в тестовый процесс.
   Проверить роли и вход, списки/карточки, Excel/PDF, скачивание документа сотрудником и отказ анонимному.
6. При настоящей аварии после успешной изолированной проверки отдельно подготовить новый сервер и UID/GID,
   адаптировать Compose/Nginx/секреты, при необходимости перевыпустить TLS и только затем переключать трафик.
   Настройки PostgreSQL-ролей и хоста создаются отдельно: `pg_dump` базы не является копией всего PostgreSQL-кластера.
   Для возобновления резервирования установить `age`, заново создать приватный `config.json` пользователя деплоя
   и файл публичного получателя; они не входят в перечисленный комплект настроек приложения.
   Не устанавливать сохранённый crontab автоматически на тестовом стенде. Приватный ключ владельца остаётся
   на Mac и в восстановленный сервер не копируется.
7. Записать источник, SHA-256, build SHA, результаты, длительности и ограничения в журнал проверок.
   Удалить временные расшифрованные данные и стенд, сохранив выбранный зашифрованный оригинал и безопасный отчёт.

Повторная совместная проверка — после внедрения этого контура, далее ориентир **раз в квартал** и после
изменений резервирования, ключа/доставки, PostgreSQL, схемы или размещения файлов. Это рекомендация;
автоматическое пробное восстановление данным cron не выполняется. Подробности:
[age](https://github.com/FiloSottile/age#readme), [pg_restore PostgreSQL 15](https://www.postgresql.org/docs/15/app-pgrestore.html).

## Границы согласованности и гарантий

Снимок PostgreSQL, количества строк и ссылки на документы согласованы через один MVCC snapshot.
Файлы — проверенная стабильная копия за время обхода, а не snapshot файловой системы на ту же наносекунду.
Нормальные загрузки используют уникальные имена `FileSystemStorage`; лишние файлы, появившиеся до обхода,
могут попасть в комплект без ссылки из снимка БД. Недостающий обязательный файл или замеченное изменение
во время копирования отменяют запуск. Произвольная внешняя перезапись файла между экспортом snapshot БД
и началом файлового обхода не восстанавливает его прежние байты автоматически. Запись сотрудникам
не блокируется; при изменениях нужен повторный запуск в спокойное окно.

Автоматическая валидация dump и скачанных байтов не заменяет восстановление БД с документами.
Расписание не является гарантированным RPO, время одного `pg_restore` — гарантированным RTO.
До фактической проверки нового комплекта нельзя объявлять подтверждённым полное восстановление после потери сервера.
