# Внешний монитор сайта и резервных копий InsFlow

## Статус и назначение

**Активирован на отдельном AMS 11.11.2026, около 20:10 МСК.**
Проверены чтение обеих ночных копий с TW, HTTPS сайта и фактическая отправка двух тестовых сообщений
в выбранный владельцем канал VK: имитация пропущенной копии и восстановление. VK подтвердил приём
обоих сообщений. Чтение сообщения владельцем этим не подтверждается.

Монитор на AMS проверяет HTTPS приложения и получает безопасный отчёт о резервных копиях с TW через
отдельный SSH-ключ. О проблемах и восстановлении сообщает в существующий канал VK. Во время работы он
читает состояние TW: команды изменения данных, перезапуски и исправления production не выполняются.
Клиентские документы, содержимое `.env`, дампы БД и квитанции VK на AMS не копируются.

## Что считается проблемой

| Проверка | Условие уведомления |
|---|---|
| `https://zs.insflow.ru/healthz/` и `/login/` | Два последовательных неуспешных наблюдения; нужны HTTP 200 без redirect, `OK` от healthz и непустая страница входа |
| SSH и корректность отчёта TW | Два последовательных неуспешных наблюдения |
| Ежедневная копия только БД, запуск 03:00 МСК | Нет подходящего успеха к 03:30 МСК |
| Полный комплект, запуск 03:15 МСК | Нет подходящего успеха к 03:45 МСК |
| Явно неуспешный запуск копирования в отчёте | Сразу после получения отчёта, без ожидания двух наблюдений |

Расписание копирования остаётся прежним: 03:00 только БД, 03:15 полный комплект; сроки учитываются в
`Europe/Moscow`. Полный комплект считается успешным только при `status=success`,
`verified_download=true`, `temporary_delivery_files_removed=true` и отсутствии `retention_warning_class`.
Отметки об отправке в VK для этого недостаточно.
Неизвестное или нечитаемое состояние не подтверждает успех.
На короткое время сборщик записывает промежуточный `last_success.json` перед очисткой. В этот момент
монитор использует только предыдущий полностью проверенный завершённый запуск, с тем же сроком годности.
Предварительная отметка нового запуска не считается подтверждённой копией.

Старая задача БД контролируется по `END success` в её журнале; такой успех включает явно обозначенную
аварийную JSON-выгрузку. Обратное скачивание, SHA-256 и завершение очистки проверяются для полного комплекта.
Проверка свежести не выполняет восстановление PostgreSQL при каждом наблюдении.

Таймер проверяет раз в две минуты. При сохраняющейся проблеме уведомление повторяется через шесть часов;
после устранения отправляется сообщение о восстановлении. Это проверка и уведомление: автоматического
восстановления сайта или резервной копии нет. Доставка уведомления зависит от доступности VK и токена.
Ошибки VK проверяются и в JSON-ответе, включая HTTP 200 с ошибкой API. Неотправленное событие хранится
приватно и повторяется со стабильным `random_id`. При множественных сбоях и восстановлениях во время
недоступности VK очередь сохраняет последний инцидент каждой проверки, максимум его сбой и восстановление.

Монитор продолжает работать при отказе TW и выключенном Mac. Отказ самого AMS или VK не может быть
надёжно сообщён этим же контуром. Токен VK на AMS необходимо обновлять отдельно при его ротации.

## Установка на AMS

Монитор — один Python-скрипт со стандартной библиотекой. Нужны Python 3.9+, timezone `Europe/Moscow`, OpenSSH client, доверенные CA
для HTTPS и systemd. Runtime запускается от отдельного пользователя и группы `insflow-monitor`.
Root требуется только для установки файлов и unit-файлов.

| Путь | Владелец и права | Назначение |
|---|---|---|
| `/opt/insflow-backup-monitor/` | `root:root`, `0755` | Неизменяемый runtime-код |
| `/opt/insflow-backup-monitor/monitor_backups.py` | `root:root`, `0644` | AMS-монитор |
| `/etc/insflow-backup-monitor/` | `root:insflow-monitor`, `0750` | Приватная конфигурация |
| `config.json`, `id_ed25519`, `known_hosts` в этом каталоге | `root:insflow-monitor`, `0640` | Конфигурация, отдельный ключ и проверенный host key TW |
| `/var/lib/insflow-backup-monitor/` | `insflow-monitor:insflow-monitor`, `0700` | Состояние наблюдений; создаётся `StateDirectory` |

Конфигурация и приватный ключ находятся вне Git и volumes приложения. В Git хранится только шаблон
контракта без реальных значений:

```json
{
  "schema_version": 1,
  "ssh": {
    "host": "<TW-SSH-host>",
    "port": 22,
    "user": "deploy",
    "identity_file": "/etc/insflow-backup-monitor/id_ed25519",
    "known_hosts_file": "/etc/insflow-backup-monitor/known_hosts"
  },
  "http_urls": [
    "https://zs.insflow.ru/healthz/",
    "https://zs.insflow.ru/login/"
  ],
  "vk": {
    "token": "<private-token>",
    "peer_id": "<private-peer-id>",
    "api_version": "5.199"
  },
  "state_file": "/var/lib/insflow-backup-monitor/state.json",
  "failure_threshold": 2,
  "repeat_seconds": 21600
}
```

Реальный токен вводится в приватный `config.json`, не передаётся через аргументы командной строки и не
публикуется в журнале. `known_hosts` заполняется по независимо проверенному ключу TW; проверку host key
не отключают. Для подключения используется отдельный ключ этого монитора, без SSH-agent и forwarding.

Файлы поставки:

- `scripts/monitoring/monitor_backups.py` → `/opt/insflow-backup-monitor/monitor_backups.py`;
- `scripts/monitoring/insflow-backup-monitor.service` → `/etc/systemd/system/`;
- `scripts/monitoring/insflow-backup-monitor.timer` → `/etc/systemd/system/`.

Unit использует `User`/`Group=insflow-monitor`, `StateDirectoryMode=0700`, `UMask=0077`,
`NoNewPrivileges`, `PrivateTmp`, `ProtectSystem=strict`, `ProtectHome=yes`. Запись разрешена в
`/var/lib/insflow-backup-monitor`; код и конфигурация доступны для чтения. На выполнение отведено 90 с,
на завершение — ещё 5 с. Период в две минуты, случайная задержка до 5 с, `Persistent=true`.
Пропущенный при выключенном AMS запуск выполняется после возвращения таймера; это не непрерывное наблюдение
за временем, когда AMS был недоступен.

## Ограничение SSH на TW

Отчёт выдаёт `report_backup_status.py`. Его устанавливают **вне Git checkout** по фиксированному пути:

```text
/home/deploy/.local/lib/insflow-backup-monitor/report_backup_status.py
```

В `authorized_keys` пользователя `deploy` для нового публичного ключа нужна отдельная строка с
ограничениями и фиксированной командой; значения ключа в документацию не включаются:

```text
restrict,command="/usr/bin/python3 -I /home/deploy/.local/lib/insflow-backup-monitor/report_backup_status.py" ssh-ed25519 <PUBLIC-KEY> insflow-monitor
```

Другие ключи деплоя не заменяются. Forced command не подставляет и не исполняет `SSH_ORIGINAL_COMMAND`,
не принимает произвольные пути/команды клиента. `-I` изолирует Python от переменных окружения и каталога
импорта. Путь вне Git не меняется при обычном `git reset` во время деплоя.

Reporter читает рабочие журналы состояния копирования и возвращает JSON schema 1 с временем наблюдения,
состояниями `jobs.database` и `jobs.recovery`. Недоступные данные обозначаются как `unknown`.
Отчёт не содержит токенов, подписанных ссылок, паролей, клиентских имён или содержимого резервных копий.

## Проверка и включение

До включения таймера оператор проверяет права, фиксированную SSH-команду и чтение безопасного отчёта.
Пользователь/группа `insflow-monitor` должны существовать. Для ручной проверки до первого запуска unit
оператор создаёт его state-каталог; далее им управляет `StateDirectory`:

```bash
sudo install -d -o insflow-monitor -g insflow-monitor -m 0700 /var/lib/insflow-backup-monitor
```

Проверка чтения конфигурации и наблюдений без отправки уведомлений:

```bash
sudo -u insflow-monitor /usr/bin/python3 -I \
  /opt/insflow-backup-monitor/monitor_backups.py \
  --config /etc/insflow-backup-monitor/config.json --check-only
```

В JSON-результате все ожидаемые `checks` должны быть `up`. Сам по себе нулевой exit code этого режима
не подтверждает исправность сайта и копий; состояния `down` нужно разобрать до активации.

Проверку порогов, повторных уведомлений и восстановления проводят на отдельной fixture/конфигурации с
отдельным `state_file`. Для имитации сбоя не останавливают production, не ломают SSH и не меняют его
резервные копии. Реальную отправку тестовых сообщений в выбранный владельцем канал VK проверяют
с явной пометкой «ТЕСТ» и отдельным состоянием, без подмены результатов рабочих копий.

После успешной проверки установка расписания выполняется оператором:

```bash
sudo systemctl daemon-reload
sudo systemctl start insflow-backup-monitor.service
sudo systemctl enable --now insflow-backup-monitor.timer
sudo systemctl list-timers insflow-backup-monitor.timer
```

Включение таймера и ручной `start` без `--check-only` разрешают реальные уведомления по конфигурации.
Этот порядок не выполнен самим добавлением файлов в Git. После активации фиксируют время, результат
чтения TW/HTTPS, проверку тестового сбоя и восстановления, доступность VK и отсутствие изменений TW.

Состояние монитора хранится в `state_file`; его нельзя использовать как доказательство фактического
восстановления данных. Проверки внешнего комплекта описаны в
[инструкции резервирования](recovery_backups.md) и [журнале восстановления](backup_restore_verification.md).

## Эксплуатационная проверка 11.11.2026

- На AMS прошли 28 изолированных тестов стандартной библиотеки: 16 для монитора и 12 для отчёта.
  Среди сценариев: отсутствие свежей копии, отдельные сроки 03:30/03:45, два сбоя связи, восстановление,
  незавершённая очистка, повреждённый отчёт, ошибка API VK, повторная доставка и 200 смен состояния при
  недоступности VK. На Mac проверки не запускались.
- `systemd-analyze verify` принял оба unit-файла. Runtime работает от `insflow-monitor`; таймер включён.
- Непривилегированный SSH-ключ получил только отчёт schema 1 даже при запросе иной команды.
  Прежние ключи сохранены. Host key TW закреплён по данным уже доверенного SSH-подключения.
- Реальное наблюдение с AMS показало `database=up`, `recovery=up`, `server=up`, `website=up`.
  Копия БД завершена 11.11 в 03:00:07 МСК, полный комплект — в 03:15:43 МСК.
- Часовой пояс TW проверен: `Europe/Moscow`, соответствует датам старого DB-журнала.
- VK подтвердил приём тестовых сбоя и восстановления; тестовое состояние затем удалено.
  Рабочее состояние монитора создаётся отдельно. Основное приложение, БД и расписание копий не менялись.
- Автоматический запуск таймера 11.11 в 20:12:04 МСК завершился с `Result=success`, `ExecMainStatus=0`.
  У всех четырёх проверок `active=false`, `failures=0`, очередь уведомлений пуста; таймер `enabled/active`.
- SHA-256 установленного кода сверены с локальными исходниками: monitor
  `2f13e159807fd7ed5227f645323c005bfcc49aa99ceed7b9be6fd615f41da31a`, reporter
  `d88eaad5644c4d5c14a0371225af0d55a92de5f6cd52a0e569dc8b016ef4cd63`.
