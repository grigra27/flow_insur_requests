# Проверка и ротация SECRET_KEY — 12.11.2026

## Причина предупреждения

На production с Django 5.2.19 `security.W009` вызван только префиксом `django-insecure-`.
Текущий ключ содержит 66 символов и 32 различных символа: требования длины и разнообразия проходят.
В 170 исторических версиях настроек, env-файлов, Compose и workflow из полного Git-репозитория
точное значение работающего ключа не найдено. Это не доказательство отсутствия утечки другими путями;
подтверждённой компрометации или недостаточной длины при этой проверке нет.

В выводе `docker compose config` символ `$` экранируется как `$$`; это представление конфигурации,
а не причина для изменения работающего ключа. Значение в исходном `.env` совпало с ключом контейнера.
Сам `.env` имеет права `0600` и не включается в Docker image.

## Изменение

Для production подготовлен новый независимый ключ из 64 случайных байтов системного генератора
(`secrets.token_urlsafe(64)`, 86 символов), без префикса разработки. Источник штатного deploy —
GitHub Actions secret `TIMEWEB_SECRET_KEY`; замена только серверного `.env` была бы потеряна при следующем выпуске.
Значения ключей не выводятся в чат, Git, аргументы команд или журналы. На Mac они не сохраняются.

Перед записью и загрузкой production-конфигурации workflow запускает
`scripts/check_production_secret_key.py`. Проверка отклоняет отсутствующий, короткий, однообразный ключ,
префикс разработки и перевод строки. Сообщение об ошибке не содержит переданного значения.
Проверка Django не отключается и не добавляется в `SILENCED_SYSTEM_CHECKS`.

Старый ключ не добавляется в `SECRET_KEY_FALLBACKS`: старые подписи перестают приниматься.
Существующим пользователям потребуется войти заново; при предварительной проверке была одна действующая сессия.
Пароли учётных записей не зависят от SECRET_KEY. Сохранённые записи и документы не переписываются.
Несохранённый черновик, находящийся только в сессии, после замены может потребовать повторного заполнения.

Основание: [проверка W009](https://docs.djangoproject.com/en/5.2/ref/checks/#security),
[назначение и ротация SECRET_KEY](https://docs.djangoproject.com/en/5.2/ref/settings/#secret-key).

## Проверки выпуска

Восемь быстрых тестов валидатора проверяют отказы на небезопасные значения и отсутствие ключа в stdout/stderr.
Полная регрессия выполняется в GitHub CI; локальный Docker и тяжёлые проверки на Mac не запускаются.

Критерии завершения:

1. Production получает именно подготовленный новый ключ из обновлённого GitHub secret.
2. `security.W009` отсутствует; `SECRET_KEY_FALLBACKS` пуст. Проверка прочих предупреждений не подавляется.
3. Новая подпись проверяется, подпись прежним ключом отклоняется.
4. После штатной выкладки работают БД, HTTPS, страницы сотрудника и защищённые документы.
5. Полный комплект с новой конфигурацией доставлен в VK и проверен обратным скачиванием.

Окончательные результаты сохраняются в pull request и workflow выпуска, безопасный операторский отчёт —
в каталоге `insflow-secret-key-rotation` за 12.11.2026. Прочие production-настройки и ключи не меняются.
