## 1. Депрекейт V1 и старых полей объекта (фаза D) — сделано 2026-10-14

Решение владельца 2026-10-13: внешних потребителей JSON-выгрузки нет — `asset_status` и `vehicle_info` можно убрать из схемы без выпуска v3.

Источник: [legacy_object_fields_deprecation.md](legacy_object_fields_deprecation.md) (фазы A–C сделаны).
Решение владельца 2026-10-13: делать сейчас.

Факты на проде (2026-10-13, только чтение):
- 343 заявки: 201 загружена старым загрузчиком V1 (10.11.2025–10.06.2026), 142 — парсером V2 (с 09.06.2026).
  Через V1 (`/upload-old/`) за последние 60 дней не загружено ни одной заявки.
- У всех 201 заявки V1 объект хранится **только** в `vehicle_info` (структуры и `object_description` нет);
  `asset_status` заполнен у 72 из них. У V2-заявок `object_description` есть у всех; `vehicle_info` — у 20,
  `asset_status` — у 54 (запасная запись, когда состояние объекта не распознано).
- Ссылки в коде: `vehicle_info` — 16 файлов (+27 файлов тестов), `asset_status` — 22 файла, включая схему
  JSON v2 (`docs/insurance_request_format_package/insurance_request_schema_v2.json`) и примеры к ней.

Решение владельца 2026-10-13: **мягкий вариант** — столбцы `vehicle_info` и `asset_status` не удаляем, они остаются
замороженным архивом V1 (в админке — свёрнутый блок только для чтения); код их не читает и не пишет.

- **D1 — сделано** (`fbeed7c`): загрузчик V1 удалён (маршрут `/upload-old/`, представление, форма, `ExcelReader`,
  тесты ячеек V1, скрипт аудита покрытия).
- **D3 — команда готова** (`b4c4e3b`): `migrate_legacy_object_fields` — отчёт / `--apply`. Отчёт на проде 2026-10-13:
  201 заявка → `object_description` из `vehicle_info`, 72 → `condition` (51 «новое», 21 «б/у»), неразобранных нет;
  у 192 заявок в сводке объекта появится год выпуска.
- **D2 — сделано в коде**: модель читает только `object_description` / `condition`; парсер переводит «новое/б/у»
  из бланка в `condition`; на превью без таблицы объектов — поля «Описание предмета лизинга» и «Состояние»;
  форма редактирования — поле «Описание объекта»; экспорт, классификатор, учёт правок, схема JSON v2 — без
  старых полей.

**Выкачено 2026-10-14** в обязательном порядке: пуш D1 + D3 → на проде бэкап `pgdump_20261014_142416.dump` и
`migrate_legacy_object_fields --apply` (обновлено 201 заявка; без описания объекта — 0, состояние только в архиве — 0;
«дата изменения» заявок не тронута) → пуш D2 (миграция `0050` — только подписи полей). После выката: ошибок в логах нет,
сводки объектов старых заявок с годом, своды V1 и V2, карточка и редактирование заявки открываются.

## 3. Ответ страховщика V2: новые блоки и уборка данных — выкачено 2026-10-14

Источник: [insurer_response_v2.md](insurer_response_v2.md) §10 (этапы 0–6 сделаны, шаблон открыт сотрудникам 07.10).
Решения владельца 2026-10-14 по кандидатам в блоки:

- **Согласование СБ / андеррайтера — сознательно НЕ делаем.** Если дать страховщикам такое поле, они будут
  отмечать «требуется согласование» почти всегда — и блок превратится в формальность. Сейчас они вписывают это
  в примечание сами и редко, только когда согласование действительно серьёзное; так и оставляем.
- **ОСВР — сделано** (решение владельца 2026-10-15, `c3803c9`, выкачено 2026-10-15; история перенесена: бэкап
  `pgdump_20261015_214221.dump`, `osvr_from_notes --apply` — 50 ответов). ОСВР — риски ущерба от военных действий
  (обстрелы, БПЛА, работа ПВО). Факты на проде: упоминается только в примечаниях СК — 50 ответов в 20 сводах; с 20.08.2026
  во всех 19 сводах Краснодара (до этого — ни в одном), в других филиалах — 1 случай. Чаще «без ОСВР» (Ингосстрах, Пари,
  Согаз); Альфа даёт «с ОСВР», иногда вторым вариантом (+16–23%).
  - **жёсткая привязка к филиалу «Краснодар»** (сюда же — Ставропольское подразделение по BRANCH_MAPPING), без галочки;
    обязателен для заявок с `OSVR_SINCE` (2026-10-16);
  - письмо: строка про ОСВР и блок шаблона; блок «Риски ОСВР»: «Включены / Включены с ограничениями / Только во втором
    варианте / Не включены» + ограничения и лимит;
  - свод V2: колонка «ОСВР», ограничения — в комментариях «ОСВР: …»; второй вариант «с ОСВР» подписан над ценником
    («Предложение 2 · с ОСВР» или «… / с ОСВР — Альфа»); свод V1 не меняется;
  - история: `osvr_from_notes` (отчёт / `--apply`) — разбор примечаний; на проде (прогон на чтение) разобраны все 50:
    36 не включены, 9 включены, 3 с ограничениями, 2 во втором варианте. Колонка показывается и в старых сводах, где ответ
    есть (`shown_sections`), но обязательным блок в них не становится.
  - **выкат:** пуш (миграция `0033`) → на проде `osvr_from_notes`, отчёт → `--apply`.
- **СМР — сделано** (решение владельца 2026-10-15, `2cd9f35`, выкачено 2026-10-15). На проде 3 заявки с «Требуется СМР» (#30 башенный
  кран, #242, #290). Блок «Страхование монтажных работ (СМР)»: «Страхуем — премия отдельно / Включено в премию по годам /
  Не страхуем» + премия за СМР (если отдельно, в ИТОГО не входит) + условия; обязателен для заявок с СМР, созданных
  с `SMR_SINCE` (2026-10-16). Свод V2 — колонка «СМР» (ответ и сумма), условия — в комментариях; свод V1 не меняется,
  как и для C/E. Письмо ссылается на блок.
- **Доп. риски КАСКО C/E — сделано в коде** (`0c428ce`, выкачено 2026-10-14; обязателен с 15.10.2026). Факты на проде (2026-10-14): 83 свода C/E,
  429 ответов СК, явно про расширенные риски пишут лишь ≈ 5–7%. Блок в шаблоне ответа: «Включены все / частично /
  не включены» + какие (если частично); обязателен для заявок C/E, созданных с `CE_RISKS_SINCE`
  (2026-10-15). Свод V2 (полный и клиентский) — колонка «Доп. риски C/E»;
  свод V1 не меняется (решение владельца). Письмо ссылается на блок шаблона.
- **Уборка данных — сделано, мягкий вариант.** Территория, примечание и исходный файл ответа
  хранились в каждой годовой строке предложения (территория — с синхронизацией между годами); теперь — в «Ответе СК»,
  он есть у каждой СК с предложениями. Поля годовых строк — архив (в админке только для чтения).
  Факты на проде (2026-10-14): 1713 пар «свод + СК», «Ответ СК» — у 50; территория по годам не расходится нигде;
  примечание различается в 661 паре, из них в 660 оно только у 1-го года — потерь при переносе нет.
  - шаг 1 (`a880545`): поля в «Ответе СК» + команда `move_offer_fields_to_responses` (отчёт / `--apply`, заполняет
    только пустое — можно повторять);
  - шаг 2: формы, загрузка файла, карточка свода, сделка и выгрузки V1/V2 читают и пишут «Ответ СК»;
    синхронизация лет и команда `unify_offer_territories` удалены.
  - **Порядок выката:** пуш до шага 1 включительно → на проде бэкап и `move_offer_fields_to_responses --apply` →
    пуш шага 2 → повторный запуск команды (догнать предложения, созданные между пушами).
  - **Выкачено 2026-10-14** в этом порядке: бэкап `pgdump_20261014_225521.dump`, `--apply` — создано 1663 «Ответа СК»,
    дополнено 50 (территория — 146, примечание — 936, файл — 50); после шага 2 повторный запуск — 0. Проверено:
    у всех пар «свод + СК» есть ответ, карточки сводов, сделки, выгрузки V1/V2 открываются, ошибок в логах нет.
