# Пайплайн свода и Excel-выгрузки

Этот документ описывает фактическую реализацию работы со сводом предложений:
от создания `InsuranceSummary` по страховой заявке до формирования и скачивания
готового `.xlsx`.

Документ предназначен для разработчиков и сотрудников, которые сопровождают
шаблоны сводов. Пользовательские действия описаны только в той степени, в
которой они влияют на технический процесс.

Архитектурное решение по территории страховщика и критерии его реализации
зафиксированы в
[`improvement_plans/insurance_offer_territory.md`](improvement_plans/insurance_offer_territory.md).

## Общая схема

```text
InsuranceRequest
    ↓ создание свода
InsuranceSummary (collecting)
    ↓ ручной ввод или загрузка ответов страховщиков
InsuranceOffer
    ↓ ручной перевод статуса
InsuranceSummary (ready)
    ↓ запрос полной или клиентской версии
ExcelExportService
    ↓ выбор full/simplified и full/client шаблона
openpyxl: заполнение заголовка, предложений и tech_info
    ↓ сохранение книги в BytesIO
HTTP-ответ с .xlsx → скачивание в браузере
```

## 1. Создание свода

Свод создаётся обработчиком `create_summary(request, request_id)`.

Перед созданием выполняются проверки:

- пользователь аутентифицирован и входит в разрешённую группу;
- у заявки ещё нет связанного свода;
- статус заявки входит в `uploaded`, `email_generated` или `emails_sent`;
- заполнены клиент, ИНН и тип страхования.

В одной транзакции создаётся:

```python
InsuranceSummary.objects.create(
    request=insurance_request,
    status="collecting",
)
```

Связь с заявкой — `OneToOneField`, поэтому у одной `InsuranceRequest` может быть
не более одного свода.

Если заявка находилась в статусе `uploaded`, текущая реализация одновременно
переводит её в `email_generated`. Это изменение статуса не генерирует текст
письма: оно является отдельным поведением обработчика создания свода.

## 2. Сбор предложений страховщиков

В свод попадают записи `InsuranceOffer`. Они могут быть созданы:

- вручную через форму добавления предложения;
- из одного загруженного Excel-ответа страховщика;
- при массовой загрузке нескольких Excel-ответов;
- копированием существующего предложения с последующим редактированием.

Ключевые данные предложения:

- страховая компания;
- номер года страхования;
- страховая сумма;
- франшиза и премия варианта 1;
- франшиза и премия варианта 2, если он есть;
- доступность рассрочки и число платежей для каждого варианта;
- территория страхования и территориальные ограничения, подтверждённые
  страховщиком (`coverage_territory`);
- примечание;
- признак `is_valid`.

На уровне базы действует ограничение:

```text
summary + company_name + insurance_year = уникальная комбинация
```

То есть у одной страховой компании не может быть двух предложений на один и
тот же год в рамках одного свода.

Счётчик `summary.total_offers` содержит количество уникальных компаний с
валидными предложениями, а не количество строк по годам.

Загрузка Excel-ответов разрешена только для свода в статусе `collecting`.
Разбор входящих ответов выполняет `ExcelResponseProcessor` из
`summaries/services/excel_services.py`.

В актуальном `flow_answer_template.xlsx` общая территория ответа указывается
в объединённой ячейке `B3:C3`; парсер читает её по адресу `B3` и копирует во
все годовые предложения одного файла. Поле необязательное, поэтому старые
ответы без этой ячейки продолжают импортироваться. После такого импорта
пользователь получает предупреждение, а свод остаётся доступен для работы.

## 3. Готовность к выгрузке

Пользователь вручную переводит свод из `collecting` в `ready`.

HTTP-обработчики полной и клиентской выгрузки разрешают генерацию только при
`summary.status == "ready"`. Для другого статуса возвращается HTTP 400.

Важно: сам `ExcelExportService` статус не проверяет. Ограничение находится на
уровне представлений Django, поэтому при прямом вызове сервиса из Python
ответственность за статус лежит на вызывающем коде.

## 4. Точки входа для генерации

| Версия | URL | Django view | Параметр сервиса |
|---|---|---|---|
| Полная | `/summaries/<id>/generate-file/` | `generate_summary_file` | `is_client_version=False` |
| Клиентская | `/summaries/<id>/generate-client-file/` | `generate_client_summary_file` | `is_client_version=True` |

Кнопки отображаются на странице свода только в статусе `ready`. JavaScript
запрашивает файл через `fetch`, проверяет HTTP-статус и MIME-тип, получает
`Blob` и инициирует скачивание.

## 5. Последовательность работы ExcelExportService

Метод `generate_summary_excel(summary, is_client_version)` выполняет операции
в следующем порядке:

1. Валидирует связанные данные.
2. Определяет полный или упрощённый формат колонок.
3. Выбирает один из четырёх файлов-шаблонов.
4. Загружает шаблон через `openpyxl.load_workbook`.
5. Заполняет шапку основного листа.
6. Группирует и заполняет предложения страховщиков.
7. Для полной версии заполняет лист `tech_info`.
8. Сохраняет книгу в `BytesIO`.
9. Возвращает буфер вызывающему Django view.

Перед генерацией обязательны:

- связанная заявка;
- номер ДФА;
- непустое описание объекта `request.object_summary`;
- название клиента.

## 6. Выбор Excel-шаблона

Используются четыре шаблона:

| Варианты предложения | Полная версия | Клиентская версия |
|---|---|---|
| Есть премия варианта 2 | `templates/summary_template.xlsx` | `templates/client_summary_template.xlsx` |
| Только вариант 1 | `templates/summary_template_simplified.xlsx` | `templates/client_summary_template_simplified.xlsx` |

Алгоритм выбора:

- если хотя бы у одного предложения `premium_with_franchise_2 > 0`,
  выбирается `full`;
- иначе выбирается `simplified`;
- при ошибке определения используется `full`.

Текущая реализация выбирает тип шаблона по `summary.offers.all()`, включая
предложения с `is_valid=False`. При заполнении строк используются только
валидные предложения. При изменении этой логики оба этапа следует менять
согласованно.

## 8. Формирование строк компаний

В выгрузку попадают только предложения с `is_valid=True`.

Данные:

- группируются по компании;
- компании сортируются по алфавиту;
- годы внутри компании сортируются по возрастанию;
- начинаются со строки 10;
- разделяются копией оформленной строки 9.

Строка 10 служит образцом стилей и формул. Для последующих строк сервис
копирует форматирование из неё, затем очищает возможные значения-заглушки и
записывает реальные данные.

Перед записью предложения проверяются:

- год страхования находится в диапазоне от 1 до 20;
- страховая сумма больше нуля;
- премия варианта 1 больше нуля;
- числовые значения неотрицательны и не превышают настроенный максимум.

Защитные лимиты генератора:

- не более 100 компаний;
- не более 10 лет на компанию;
- не более 1000 строк.

## 9. Формулы, итоги и объединение ячеек

Тарифы рассчитываются формулами Excel:

```excel
=IF(AND(C10<>0,F10<>0),F10/C10*100,"")
```

Для второго варианта вместо `F` используется `L`. При копировании строки
ссылки адаптируются к текущему номеру строки.

Для многолетнего предложения одной компании:

- название компании в колонке `A` объединяется по всем годам;
- итоговые премии суммируются и объединяются в `I` и, для полного шаблона,
  в `O`;
- территория объединяется в `P` или `J`, только если нормализованное значение
  совпадает во всех годах;
- при разных территориях или ограничениях значения остаются построчными;
- примечания по всем годам консолидируются в одну объединённую ячейку.

Для компании с одним годом итоговая премия просто копируется из колонки
премии соответствующего варианта.

Пустая территория не подменяется значением из заявки и выводится как
`Не указано страховщиком`.

## 10. Системные примечания

Помимо текста из `offer.notes`, генератор может добавить:

- `Обязателен осмотр предмета лизинга.` — если объект не распознан как новый;
- `Требуется согласование франшизы с ГО.` — если хотя бы в одном году компании
  есть ненулевая франшиза любого варианта.

Одинаковые системные примечания не дублируются. В многолетнем предложении
примечания всех лет объединяются в хронологическом порядке.

## 11. Технический лист полной версии

Лист `tech_info` заполняется только при `is_client_version=False`. Если листа
нет в шаблоне, генерация продолжается без него.

| Ячейка | Данные |
|---|---|
| `B5` | Номер заявки |
| `B6` | Клиент |
| `B7` | ИНН |
| `B8` | Филиал |
| `B11` | Тип страхования |
| `B12` | Объект страхования |
| `B13` | Банк-кредитор |
| `B14` | Запрошенный режим франшизы |
| `B15` | Запрошенная рассрочка |
| `B16` | Цели использования |
| `B17` | Описание запрошенного страхового покрытия |
| `B21` | Автозапуск |
| `B22` | Комплектность ключей |
| `B23` | ПТС/ПСМ |
| `B24` | Телематический комплекс |
| `B27` | Территория по исходной заявке |
| `B28` | Перевозка |
| `B29` | СМР |

В `B17` записывается отдельное техническое описание типа страхования,
сформированное `_get_insurance_description_for_tech_info()`. Полный текст
`request.email_body` туда не копируется.

Поля `B21`–`B24` заполняются для КАСКО и спецтехники. В `B27` остаётся именно
исходно запрошенная территория заявки; она не смешивается с ответами
страховщиков в колонках `P`/`J`. Территория заявки, перевозка и СМР
заполняются для страхования имущества.

Клиентская версия создаётся из отдельного клиентского шаблона и не вызывает
заполнение `tech_info`.

## 12. Выдача готового файла

Книга не сохраняется в `InsuranceSummary.summary_file`. Каждый запрос
генерирует новый файл в памяти.

Имена файлов:

```text
full_svod_<цифры_из_номера_ДФА>_<дд_мм_гггг>.xlsx
client_svod_<цифры_из_номера_ДФА>_<дд_мм_гггг>.xlsx
```

HTTP-ответ использует MIME-тип:

```text
application/vnd.openxmlformats-officedocument.spreadsheetml.sheet
```

## 13. Обработка ошибок

| Ситуация | Результат |
|---|---|
| Статус свода не `ready` | HTTP 400 |
| Нет обязательных данных заявки | HTTP 400 |
| Не найден или не читается шаблон | HTTP 500 |
| Ошибка заполнения или сохранения книги | HTTP 500 |
| Успешная генерация | HTTP 200 и `.xlsx` в теле ответа |

Ошибки сервиса логируются с идентификатором свода. Известные исключения:

- `InvalidSummaryDataError`;
- `TemplateNotFoundError`;
- `ExcelExportServiceError`.

## 14. Тестирование

Основной интеграционный набор:

```bash
python manage.py test summaries.test_excel_integration summaries.test_offer_coverage_territory
```

Полный рекомендуемый набор проекта:

```bash
python manage.py test insurance_requests.tests summaries.test_company_matcher summaries.test_templatetags
```

Интеграционные тесты проверяют:

- создание свода;
- ограничение генерации по статусу;
- возврат корректного MIME-типа;
- формирование валидного `.xlsx`;
- заполнение `C1`, `C2`, `C3`;
- несколько компаний и лет;
- импорт, отображение и выгрузку территории страховщика во всех четырёх
  шаблонах;
- объединение одинаковых и сохранение разных территорий по годам;
- обратную совместимость с ответами без `B3`;
- длинные строки и специальные символы;
- обработку ошибок сервиса.

Большая часть интеграционных тестов подменяет производственные шаблоны
минимальной временной книгой. Поэтому после изменения реальных шаблонов нужно
дополнительно проверять обе версии на тестовом своде вручную.

## 15. Как безопасно менять генератор

При изменении структуры свода:

1. Обновить соответствующий маппинг колонок или `TECH_INFO_CELLS`.
2. Синхронно изменить все затронутые шаблоны: полный, упрощённый, клиентский.
3. Проверить строку 10 — источник стилей и формул.
4. Проверить строку 9 — источник разделителя.
5. Проверить однолетнее и многолетнее предложение.
6. Проверить наличие и отсутствие второго варианта франшизы.
7. Проверить полную и клиентскую выгрузки.
8. Добавить или обновить автоматические тесты.
9. Открыть все затронутые результаты в Excel или LibreOffice и проверить формулы,
   объединения, перенос текста и печатную область.
